# /token-ops:effort-router — タスク規模に応じた effort/モデル選定

着手しようとしているタスクの規模・不確実性・リスクを見積もり、**過不足のない effort レベル・モデル・実行モード**を推奨します。
目的は「小さいタスクに大きな計算を使わない／大きいタスクに小さな計算で挑まない」ことで、品質を保ちながらトークンを節約することです。

`$ARGUMENTS` にタスクの説明があればそれを対象に、無ければ直近のユーザー指示や現在の差分(`git status` / `git diff`)から対象タスクを推定します。

## 前提: 調整できるつまみ (Claude Code)

| つまみ | コマンド | 効果 |
|---|---|---|
| effort レベル | `/effort <level>` | `low` / `medium` / `high`(既定) / `xhigh` / `max`。**応答の全トークン**(本文・ツール呼び出し・思考)の量を制御 |
| ultracode | `/effort` → ultracode | `xhigh` 相当 ＋ **dynamic workflows** の自動オーケストレーション (セッション限定) |
| モデル | `/model <name>` | `haiku`(軽量) / `sonnet`(中) / `opus`(高) |
| fast mode | `/fast` | Opus を高速化(Opus 5 / 4.8 / 4.7 で利用可。小さいモデルには劣化しない)。**1トークン単価は上がる**。対話的反復向き、長時間自律処理には不向き |
| プランモード | Plan mode | 実装前に計画を立て、承認を得てから動く |
| 一発だけ熟考 | `ultrathink` をプロンプトに含める | セッションの effort を変えずに、その1ターンだけ深く推論させる |

> 注: モデルを切り替えると effort はそのモデルの既定値に戻る。`low` などを使いたい場合は `/model` の**後**に `/effort` を設定する。
> `max` と `ultracode` はセッション限定で永続しない。
> effort を下げるとツール呼び出しの**回数**も減る(前置きを省いて動く、複数の操作をまとめる)。逆に上げると調査が広がる。

## effort で制御できないもの

**effort は思考量を制御するが、可視応答の長さは確実には縮まらない。** effort を下げても、ユーザーに見える回答やディスクに書き出すドキュメントの長さはあまり変わらない。出力を短くしたいなら、effort ではなくプロンプトで直接指示する。

つまり「トークンを節約したい」への答えは 2 本立てになる。

1. **effort / モデルを下げる** — 思考とツール呼び出しのトークンを削る(このスキルの本体)。
2. **簡潔さを指示する** — 可視出力のトークンを削る。例:
   > 回答は要点に絞る。前置きや注意書きは短くし、本題に文量を割く。説明を求められたら、詳細を明示的に要求されない限り概要にとどめる。

作業中のナレーション(実況)も effort では減らない。長い agentic 作業で実況が多いと感じたら、望ましいケイデンスを明示する。

> 最初のツール呼び出し前に、何をするかを1文で述べる。作業中は重要な発見か方針転換があったときだけ短く報告する。完了時は結論から始める。

## 判定軸

タスクを次の4軸で評価します。

1. **規模 (scope)**: 触るファイル/システムの数。1行か、単一ファイルか、横断的か。
2. **不確実性 (uncertainty)**: 方針が明確か、設計判断や調査が要る探索的タスクか。
3. **可逆性/リスク (reversibility)**: 失敗の戻しやすさ。本番・データ・外部影響があるか。
4. **反復性 (iteration)**: 短いフィードバックループを高速に回したいか(対話的デバッグ等)。

## ルーブリック

| ティア | 特徴 | effort | モデル | fast | プランモード | dynamic workflow | 例 |
|---|---|---|---|---|---|---|---|
| **T0 雑務** | 1行・typo・単純質問・完全に可逆 | `low` | haiku / sonnet | 対話時◯ | 不要 | 不要 | typo修正、事実1問、設定値の確認 |
| **T1 小** | 単一ファイル・スコープ明確・低リスク | `low`〜`medium` | sonnet | 反復時◯ | 不要 | 不要 | 小バグ修正、小機能、lint対応 |
| **T2 中** | 複数ファイル・方針はほぼ固まっている | `medium`〜`high`(既定) | sonnet / opus | 反復時◯ | 推奨 | 不要 | リファクタ、機能実装、renovate/mise設定、CI修正 |
| **T3 大** | 横断的・設計判断あり・不確実・高リスク | `xhigh`(必要なら `max`) | opus | ✕(長時間自律) | 必須 | 任意 | DB/パッケージマネージャ移行、アーキ変更、CI基盤刷新 |
| **T4 探索/監査** | 広域調査・網羅監査・多観点レビュー | `low`〜`medium` で1パス → 疑わしい箇所だけ `xhigh` | opus | ✕ | 必須級 | 独立・並列可能なときのみ | 大規模監査、横断調査、多観点コードレビュー |

### 追加の判断

- **1ステップだけ難しい**: 全体は T1〜T2 だが特定の設計判断だけ難しい → effort は上げず、その箇所で `ultrathink` を使う。
- **レビュー/監査は段階的に**: コードレビューやバグ探しは低 effort でも精度が落ちにくい。まず `low`/`medium` で1パス通し、取りこぼしが疑わしい箇所だけ effort を上げて深掘りする。最初から `max` で回すより安い。
- **レビューの絞り込みは別パスで**: 「重大なものだけ報告して」のような指示は文字どおり受け取られ、報告そのものが減る。まず気づいた点を全部挙げさせ、重要度の切り分けは別のステップで行う。
- **コンテキストが重い調査**: 多数のファイルを読む必要がある → メインの文脈を汚さないよう**サブエージェント/Workflow に調査を外出し**し、結論だけ受け取る(トークン効率↑)。ただし委譲は次の範囲に留める。
  - 大きく独立して並列化できる作業(広域の多ファイル調査など)にだけ委譲する。
  - 数回のツール呼び出しで自分で終わる作業は委譲しない。
  - **自分の作業の検証・二重チェックには使わない**(自己修正は既定で行われるため、二重に走らせるとコストだけ増える)。
  - 1エージェントで足りるなら1つに留め、起動数を低く保つ。
- **コスト最優先のバッチ/自律処理**: fast mode は使わず(単価高)、effort も必要最小限に。
- **対話的な高速反復**: fast mode ◯。ただしセッション途中の有効化は累積コンテキストに一度課金されるため、最初から有効が効率的。

## 実行手順

1. **対象タスクの特定**: `$ARGUMENTS` または直近の指示・差分から、これから行うタスクを1〜2文で要約する。
2. **4軸の評価**: 規模・不確実性・可逆性・反復性を一言ずつ評価する。曖昧なら不明点を述べる。
3. **ティア判定**: ルーブリックから T0〜T4 を選ぶ。境界上なら、可逆性が低い/不確実性が高いほど上のティアへ寄せる。
4. **推奨の提示**: 下記フォーマットで、推奨設定と**適用コマンド**、理由を出力する。出力が長くなりがちなタスク(レビュー、調査報告、ドキュメント生成)なら、簡潔さ指示もあわせて提示する。
5. **AI 自身の振る舞いへの反映**: 推奨が出たら、AI 側で制御できる範囲(プランモードに入る、Workflow を使う、`ultrathink` する、調査を外出しする)は自律的に適用してよい。外出しは上記「コンテキストが重い調査」の範囲に留める。`/effort` `/model` `/fast` のようなセッション設定はユーザーに適用を促す。

## 設計思想

- **既定は `high`、そこから下げる**。まず既定の `high` から始め、品質が保てる範囲で `low`/`medium` へ**積極的に下げる**。これがトークン効率の主レバー。
- **上げるのは大物だけ**。`xhigh` は要求の厳しいコーディング/agentic 作業に、`max` は無制約のトークン支出が正当化されるタスクにだけ使う。安易に上げない(過剰思考でトークンを浪費しうる)。
- **旧モデルの既定を流用しない**。以前のモデル向けに決めた effort 設定をそのまま持ち込まず、実際のタスクに当てて測り直す。
- **effort と出力長は別のつまみ**。トークンを削りたいなら effort を下げるだけでなく、簡潔さも明示的に指示する(→「effort で制御できないもの」)。
- **局所的な熟考は ultrathink**、**重い調査は外出し**(ただし委譲は独立した大物に限る)。セッション全体の effort を上げずにピンポイントで深掘りするのがトークン効率の要。
